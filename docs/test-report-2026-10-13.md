## 缺陷清单

中等严重度表示特定操作导致错误选择、记录隐藏或业务流程受阻；低严重度表示错误输入的处理和提示有问题。未在本轮覆盖场景中发现绕过收退款上限、负库存或跨顾客写入成功。

| 编号 | 严重度 | 问题 | 影响 |
|---|---|---|---|
| QA-01 | 中 | 首页宠物预约入口没有保留所点宠物 | 点猫咪预约后实际默认选狗狗 |
| QA-02 | 中 | 预约管理与收款页面共享隐藏筛选状态 | 切页后部分猫狗预约被隐藏，看起来像缺少账单 |
| QA-03 | 中 | 标准耗材停用后，下拉框显示与提交值不一致 | 表面选择可用耗材，提交却携带停用耗材，护理不能完成 |
| QA-04 | 中 | 有未完成护理任务的员工可直接改成前台角色 | 原任务仍分配给员工，但该账号失去护理权限 |
| QA-05 | 中 | 前台可被授予护理资质并成为排程候选 | 可用资源结果包含不能执行护理的账号 |

### QA-01：首页预约选择错误

复现：使用顾客账号登录，在首页 **Luna** 旁点击“预约”。

期望：预约表单选择 Luna，并展示猫咪服务与价格。  
实际：“宠物 1”值为 `1`（Mochi），而不是 `2`（Luna），因此显示狗狗服务。猫咪服务本身存在；手动改选 Luna 后流程正常。

定位：[main.tsx 第 45 行](../frontend/src/main.tsx#L45) 的每只宠物按钮只调用 `go('booking')`；[第 53 行](../frontend/src/main.tsx#L53) 初始化固定取 `pets[0]`。

修复建议：把所点 pet_id 传给预约页，校验归属和启用状态后预选；普通导航进入时使用明确的默认选择。  
临时办法：在预约页先手动选择正确的宠物。

证据：`audit.spec.ts` 中 `homepage pet booking must retain the clicked cat`。

### QA-02：收款页面沿用不可见的筛选条件

复现：前台进入“预约管理” → 点击“已确认” → 左侧切到“收款记录”。

期望：收款页使用自身的“全部 / 待收款 / 待退款”筛选，当前条件可见。  
实际：内部仍保留 `status='confirmed'`，但当前页面没有该筛选按钮；三个按钮均为 `aria-pressed=false`，列表只剩已确认预约。已完成或护理中的猫咪预约也被隐藏。

定位：[main.tsx 第 39 行](../frontend/src/main.tsx#L39) 在两个页面复用同一 `Appointments` 组件；[第 79 行](../frontend/src/main.tsx#L79) 的本地状态不会随 `finance` 改变而重置。

修复建议：两个页面使用不同组件 key 或独立筛选状态；模式切换时清除该模式不支持的状态。  
临时办法：进入收款页后再点击一次“全部”。

证据：`audit.spec.ts` 中 `changing to finance must not preserve a hidden appointment status filter`。

### QA-03：停用耗材后出现不可见的旧选择

复现：店长在“耗材库存 → 耗材目录”停用“温和洗毛液”；随后 Mia 打开 Nori 正在进行的洗护，进入完成护理表单并提交。

期望：停用耗材要明确标注并要求重新选择，或从默认用量中清除；提交的耗材必须与界面所示一致。  
实际：标准配方仍保留洗毛液 ID 1，但下拉选项把它过滤掉。浏览器实际显示的选择 ID 为 `[3,2]`，提交 JSON 仍是 `[1,2]`；接口返回 **409：不能使用已停用的耗材**。第一个下拉框显示棉片，旁边单位仍按原洗毛液显示 mL。

定位：[main.tsx 第 109 行](../frontend/src/main.tsx#L109) `UseRows` 过滤选项但没有同步行数据；`CompleteModal` 从标准配方直接初始化全部用量。

修复建议：停用配方引用项时明确处理其影响；表单必须显示失效项及原因，或者过滤并提示重新核对用量，不能让 DOM 选择与状态不同。  
临时办法：移除失效耗材行后，重新添加实际使用的有效耗材，并核对单位。

证据：`audit.spec.ts` 中 `displayed consumables must match submitted IDs after a recipe ingredient is disabled`。后端拒绝请求，未发生错误库存扣减。

### QA-04：角色变更使已有任务失去执行人权限

复现：Emma 仍有未开始任务时，店长把她的角色从“护理师”改成“前台”；Emma 再开始原任务。

期望：阻止此类角色变更并提示先处理未结束任务，或者提供一致的任务转交流程。  
实际：更新角色返回 **200**；原任务依旧分配给 Emma，但她开始护理返回 **403**。

定位：[catalog.py 第 88 行](../backend/catalog.py#L88) 的 `employee_write` 只在停用账号时检查未结束任务，改变职能角色时没有相同保护；`care_item` 仅允许护理师和店长。

修复建议：角色变更时检查该员工现有任务是否仍可执行；对需要转交的任务先完成或重新安排。应覆盖 scheduled 和 in_progress，不能只检查账号启用状态。

证据：`test_audit_cannot_remove_groomer_role_with_assigned_tasks`。测试 finally 恢复测试员工的原角色。

### QA-05：排程候选与操作权限不一致

复现：店长给前台账号添加猫咪洗护资质和覆盖时段的班次；前台查询该时段猫咪洗护的可用员工。

期望：候选员工必须具备执行护理流程所需的权限，或系统明确支持并实现兼岗。  
实际：候选结果包含 `employee_id=2` 的前台账号；该角色在护理开始/完成接口没有权限。

定位：[catalog.py 第 115 行](../backend/catalog.py#L115) 接受任意员工的护理资质；[bookings.py 第 108 行](../backend/bookings.py#L108) 和数据库安排触发器校验启用、资质与班次，但不校验可执行护理的角色。

修复建议：统一资质维护、可用员工查询、最终分配和护理接口的角色规则；若允许兼岗，应先明确权限模型。不能仅在前端下拉框隐藏前台。

证据：`test_audit_receptionist_not_offered_for_grooming`。这是 QA-04 的相关规则问题，但入口不同：QA-04 是已有任务后的角色改变，本项是新安排的候选生成。

### QA-06：排班日期错误返回数据库故障

复现：已登录店长请求 `/api/shifts?start=not-a-date&end=2026-10-14`。

期望：HTTP 422 或明确的日期校验提示。  
实际：SQL 转换日期失败，返回 **HTTP 503：数据库暂时不可用，请检查本地数据库状态**，但数据库本身正常。

定位：[catalog.py 第 135 行](../backend/catalog.py#L135) 的 start/end 类型是 str，直接进入 SQL `::date`；通用数据库异常处理把该错误归为服务不可用。

修复建议：使用 date 参数类型，在进入 SQL 前检查日期格式、先后顺序与查询范围；界面处理日期被清空的情况。

证据：`test_audit_invalid_shift_date_is_validation_error`，JUnit 中保留了实际响应。

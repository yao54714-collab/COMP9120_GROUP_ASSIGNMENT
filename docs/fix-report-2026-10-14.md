## 数据保留与本地实例

修复前完整备份位于 `.runtime/backups/20261014-225726/pawcare.dump`，同目录 `business-data.json` 保存 18 张业务表的行数与内容校验值。备份包含实际业务数据，应保留在本机，不随源码分享。

测试写入全部发生在随机命名的独立测试库。实际 `pawcare` 数据库只执行新增函数、触发器和版本记录的增量迁移；没有重置、重新填充或清空业务表。重启后 18 张表的行数及完整内容校验值均与修复前相同，包括 14 个预约、6 只宠物、7 条收款和 4 位员工。`auth_session` 与 `schema_version` 为技术表，不计入业务数据一致性比较。

网站为 http://127.0.0.1:8000；在 VS Code 中仍运行 `run.py`。pgAdmin 使用原有 55432 端口的 PawCare 连接，schema `pawcare` 仍有 20 张表、3 个视图。刷新网页即可加载修复后的界面；数据库结构清单已更新到 [schema-inventory.json](schema-inventory.json)。

## 六项修复

| 编号 | 修复后的行为 | 验证方式 |
|---|---|---|
| QA-01 | 首页点击 Luna 的预约按钮，预约表单预选 Luna 并显示猫咪服务；只接受当前顾客的有效宠物 | Chrome 操作首页入口，断言 pet_id=2；猫咪完整预约及 A$110 收款流程 |
| QA-02 | 预约与收款页面分别初始化筛选状态，切到收款页默认显示“全部” | Chrome 先选“已确认”，再切收款页，检查当前筛选与完整列表 |
| QA-03 | 停用耗材保持可见并明确标注，移除或替换前禁止提交；显示值与请求值一致，后端拒绝将停用耗材加入标准配方 | Chrome 停用默认耗材、检查警告、替换后完成护理；API 检查失败时原配方不变 |
| QA-04 | 员工有待开始或进行中护理任务时，禁止改为前台或停用；护理师升为店长仍能完成任务 | API 验证两种任务状态；直接 SQL 验证数据库触发器 |
| QA-05 | 资质授予、候选查询、默认选择及最终分配统一限制为护理师或店长；保留历史资质的前台也不会成为候选 | API 检查新资质与最终安排；Chrome 检查历史资质下默认选 Mia，候选中没有前台 |
| QA-06 | 非法日期、空日期、倒置范围和过长范围返回 422；界面清空日期时显示输入提示，恢复日期后正常查询 | API 边界用例；Chrome 清空并恢复日期 |

数据库使用 `05_care_roles.sql` 增量迁移，新增角色保护触发器。业务表字段、主外键与函数依赖不变，原有 3NF/BCNF 分析仍适用。历史资质、护理与资金记录保留。

## 本轮覆盖

- 猫狗、多宠物及多服务预约，确认资源、护理开始和完成、实际耗材扣减、分次收款与取消退款。

- 报表与原始流水对账、店长入库和配方维护、四种角色全部导航、桌面和 375 px 手机布局、浏览器 JavaScript 错误检查。

## 重现命令

先运行 `run.py` 启动项目数据库，再在项目根目录执行：

```powershell
.\.venv\Scripts\python.exe -m pytest -q --junitxml=test-results/fixed-backend.xml
.\.venv\Scripts\python.exe tools\check_browser.py
```

前端构建：在 `frontend` 执行 `npm run build`。测试分别创建随机命名的独立数据库，结束后仅清理自己创建的测试库。

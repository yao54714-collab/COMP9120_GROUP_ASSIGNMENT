# PawCare 事务、验证与展示说明

## 事务怎样对应门店操作

后端每个写请求使用一个 Psycopg 连接上下文。成功退出时 COMMIT；SQL 或业务检查抛出异常时 ROLLBACK。HTTP 409 表示业务冲突，前端保留表单并显示原因。参数通过 Psycopg 参数绑定传入 SQL，不能将用户输入拼成 SQL。

| 操作 | 一个事务中的内容 | 失败时的结果 |
|---|---|---|
| 注册 | 创建账号、顾客档案与账号绑定 | 邮箱重复时三者均不新增 |
| 提交预约 | 校验顾客归属、创建预约头与至少一个服务项 | 任一宠物或服务无效，不留下空预约 |
| 确认安排 | 检查全部待安排项，写入员工、工位、时间、历史报价 | 任一项冲突，其他项也恢复原状 |
| 开始护理 | 建立护理记录，切换服务项为 in_progress | 两者同时成功或失败 |
| 完成护理 | 写实际耗材流水及来源，写护理结果/结束时间，完成服务项，更新当前体重 | 缺货或约束失败时所有变更回滚，不产生半份护理记录 |
| 收款 | 锁定预约、校验余额与请求编号、创建收款流水 | 超额、重用不同内容的请求编号被拒绝 |
| 取消与退款 | 取消改变应收；退款单独选择原收款，校验可退余额 | 退款不得超原收款剩余可退部分或预约总可退余额 |
| 库存入库/报损/调整 | 锁定耗材、检查请求编号、追加库存流水 | 不能将余额变成负数；不覆写旧流水 |

取消和退款是两个真实业务步骤：取消不会伪造已经退给顾客的钱；只有店长完成线下退款后才登记退款流水。支付方式 cash/card/transfer 是线下记录，不对接银行。

## 并发与完整性

默认隔离级别为 PostgreSQL READ COMMITTED。单店规模下，安排、人员资质/排班和相关服务状态变更共用事务级 advisory lock `(9120,1)`，保证冲突校验与写入作为一个整体执行。该锁在 COMMIT/ROLLBACK 时自动释放。它降低同店同时排程的吞吐量，换取简单可解释的一致性；不是面向大量连锁门店的并发设计。

数据库另有四个 GiST 排除约束：员工班次不重叠；活动服务的员工、工位、宠物各自不重叠。时间采用半开区间 `[start,end)`，前一项 10:45 结束时，后一项可以 10:45 开始。可用资源查询只是建议；最终确认仍在事务中重新校验。

收退款对同一预约执行 `SELECT ... FOR UPDATE`。库存写入先锁耗材主行，护理完成按 consumable_id 排序取得锁；负库存检查与流水插入一起执行。统一的取锁顺序降低死锁机会，8 秒锁等待超时向用户返回可重试的冲突信息。数据库锁不是页面上的“禁用按钮”，不同客户端仍受保护。

库存流水、收款、退款不可更新或删除。完成的护理记录不可覆盖。服务状态与护理记录、库存 use 流水与来源的约束在提交时检查，因此事务内部允许短暂的先后写入，提交时必须一致。保护代码位于 `database/02_rules.sql`、`04_hardening.sql` 和 `05_care_roles.sql`。

护理资质、可用资源和最终分配统一要求护理师或店长角色。已有未结束任务时，角色变更或停用被 API 与数据库触发器共同阻止。前台保留的历史资质不会成为护理分配候选。标准配方中的耗材停用后，完成护理表单明确显示失效项并阻止提交；用户移除或替换后才能继续，后端也会再次检查耗材有效性。

收款、退款、手工库存变动使用唯一 `request_key`。相同编号、相同内容再次提交会返回原记录；相同编号换内容被拒绝。护理完成通过状态转换与固定领用键避免重复扣库存。前端操作期间也禁用提交按钮，但数据库约束才是最终保障。

## SQL 与界面的对应

| SQL 示例 | 用途与展示点 |
|---|---|
| Q1 多表 JOIN | 今日工作台连接预约、顾客、宠物、服务、员工和工位 |
| Q2 EXISTS / NOT EXISTS | 符合资质、班次、物种、工位及占用条件的员工与工位组合 |
| Q3 视图聚合 | 包含尚未入库耗材的库存余额与低库存提示 |
| Q4 两视图 JOIN | 已完成但仍未收齐的预约 |
| Q5 GROUP BY | 已完成服务的数量与约定服务价值 |
| Q6 HAVING | 有历史服务但三个月未回访的顾客分析查询 |
| Q7 UNION ALL + CTE | 收款与负数退款合并为按发生日统计的净收款 |

`database/03_queries.sql` 可在 pgAdmin Query Tool 运行。Q2 的示例日期需要按演示日期调整。实际 API 的参数化查询位于 `backend/bookings.py`、`catalog.py` 和 `api.py`。Q6 是提供给数据库展示的分析查询，没有独立营销发送页面。

报表将“服务价值”和“实际收款”分开。已完成服务按实际结束日期统计；已完成预约要求全部服务项结束且至少一项完成，归入最后一项完成护理的日期；收退款按资金流水发生日期统计。多项服务、分次付款、退款先分别聚合，避免 JOIN 行数膨胀使金额重复累计。日期边界统一为 Australia/Sydney。

## 可重现验证

先运行 `run.py` 使数据库可连接，再从项目目录运行：

```powershell
.\.venv\Scripts\python.exe -m pytest -q --junitxml=test-results/backend.xml
.\.venv\Scripts\python.exe tools\check_browser.py
cd frontend
npm run build
```

后端测试和浏览器测试分别新建随机命名的测试库，并在 finally 中只删除本次测试创建的库。演示库 pawcare 不清空、不重置。测试账号与资料均为人工构造。

后端测试验证：角色与顾客数据隔离、宠物物种匹配、多项安排整体回滚、员工资质/班次/工位、并发抢占只成功一次、完整护理与历史价格、缺货回滚、分次收款与退款上限、重复请求、并发防超收、不可变流水、员工与班次维护、注册/登出/来源检查、报表与原始流水对账、部分完成口径、历史与身份保护。

浏览器测试使用本机 Chrome：通过真实页面新增宠物、预约、前台确认、护理师完成、前台收款；逐个角色检查导航页面、桌面/手机横向溢出及 JavaScript 错误；验证店长入库与标准耗材维护。报告与截图在 `test-results`。2026-10-14 的历史回归为 32 项后端与 10 项浏览器测试，见 [修复报告](fix-report-2026-10-14.md) 和 `test-results/fixed-backend.xml`。2026-10-15 英文版和用户管理扩展至 46 项后端、14 项浏览器测试，当前 `test-results/browser.json` 对应本轮，见 [本轮报告](english-and-accounts-2026-10-15.md)。

数据库结构可重新导出：

```powershell
.\.venv\Scripts\python.exe tools\inspect_database.py
```

生成的 `schema-inventory.json` 只包含结构、约束、行数和时间，不包含顾客数据或密码。实际包含 18 张业务表、auth_session / schema_version 两张技术表、3 个视图。

## 三分钟演示脚本

建议预先打开网站登录页和 pgAdmin，准备四个账号，选明天 10:00 的空档，避免把临时找菜单计入视频时间。

| 时间 | 操作和解说 |
|---|---|
| 0:00–0:20 | 介绍一家单店的四个角色，展示顾客端与商户端的不同风格 |
| 0:20–0:45 | 顾客登录，为 Mochi 选犬类洗护并提交明天的预约 |
| 0:45–1:15 | 前台切到明天，打开待确认预约，用可用组合安排 Emma 与洗护工位，确认报价 |
| 1:15–1:45 | Emma 切到明天的任务，开始护理，填写结果和实际耗材，点击完成 |
| 1:45–2:05 | 前台收款，展示余额归零；顾客查看新增护理记录 |
| 2:05–2:30 | 店长查看库存扣减和经营报表，说明服务价值与现金实收的区别 |
| 2:30–3:00 | pgAdmin 展开表与视图，说明 M:N 关系、BCNF 的依赖依据，以及缺货回滚/并发测试证据 |

为方便现场快速展示，护理师可以提前开始已确认的未来任务；系统记录真实点击时间作为实际开始/结束时间。因此演示中选择明天的预约后，完成护理与收款会出现在今天的报表。正式门店可进一步加入到店签到和开始时间窗口。

本目录提供实现说明与脚本，不代替实际录制的视频、小组真实贡献记录或课程指定版式的提交文件。当前实现的边界是本机单店应用；寄养、零售、营销短信、线上支付和完成服务后的赔偿处理未纳入本版。
